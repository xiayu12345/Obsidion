libinflist 数据流与协作

本文用思维导图 / 时序图说明各模块如何协作、JSON 与图片如何从「滑动」一路流到「刷新 cell」，以及 reset/close 为什么不会野指针。

渲染图需要支持 Mermaid 的预览器（VS Code 装 Markdown Preview Mermaid Support，或 GitHub 直接渲染）。

1. 模块分层（谁依赖谁）

graph TD
    APP["业务 App<br/>(拼 URL / cJSON 解析 / http 下载)"]
    subgraph LIB["libinflist.so"]
        CORE["core/ inflist_core<br/>单例 · 扇出 · 定时器 tick"]
        GRID["render/ inflist_grid<br/>虚拟网格 · cell 复用 · 滑动/翻页/点击"]
        TXT["text/ inflist_text<br/>页 LRU · generation · 静态收件箱"]
        IMG["image/ inflist_image<br/>id LRU · generation · 静态收件箱"]
    end
    HTTP["libhttp_client.so"]
    LVGL["liblvgl.so"]

    APP -->|inflist_open/reset/close<br/>commit_item / notify_*| CORE
    CORE --> GRID
    CORE --> TXT
    CORE --> IMG
    GRID -->|lv_obj_*| LVGL
    CORE -->|回调 request_page/image| APP
    APP -->|http_download| HTTP
    HTTP -->|完成回调(worker线程)| APP

    classDef lib fill:#1f6feb,stroke:#0b2e6b,color:#fff;
    classDef ext fill:#6e7681,stroke:#30363d,color:#fff;

要点：

  • 文字库与图片库互不引用（互不 include），只由协调层粘合。
  • 库自己不下载：缺数据时回调业务，业务用 libhttp_client 下载。
  • 渲染核心不认识业务，只通过 ops 回调向协调层取数据。

2. JSON 文字流（从滑动到刷新）

sequenceDiagram
    autonumber
    participant U as 用户(滑动)
    participant G as inflist_grid (UI线程)
    participant C as inflist_core (UI线程)
    participant T as inflist_text
    participant I_ as inflist_image
    participant A as 业务 App
    participant H as libhttp_client (worker线程)
    participant TK as 定时器 tick (UI线程)

    U->>G: 滑动 → 需要 id 的 cell
    G->>C: get_item(id)
    C->>T: inflist_text_get(id)
    alt 命中且就绪
        T-->>C: title/subtitle (库内常驻指针)
        C-->>G: 填充 cell ✅
    else 缺页
        T->>T: 占槽·标记 loading·gen=当前代次
        T->>C: request_page(page, gen)
        C->>A: request_page(page, gen)
        A->>H: http_download(json, ...) [gen 存进 user_data]
        Note over G,C: UI 线程不阻塞，cell 先显示占位
        H-->>A: 下载完成 (worker线程)
        A->>C: inflist_notify_page(gen, page, path, ok)
        C->>T: inflist_text_notify_page → 只写静态收件箱(加锁)
        Note over T: worker 线程到此为止，绝不碰库/LVGL
        TK->>T: inflist_text_tick() 排空收件箱
        T->>T: 校验 gen：陈旧则丢弃
        T->>A: parse_page(page, gen, path)
        A->>C: 逐条 inflist_commit_item(gen,id,title,sub,img_url)
        C->>T: inflist_text_set_item(写文字)
        C->>I_: inflist_image_set_url(写图片URL)
        T->>C: on_committed(first_id, count)
        C->>G: notify_range → 重绑这批 cell ✅
        C->>G: request_visible_images → 踢图片请求
    end

3. 图片流（与文字流并行、独立）

sequenceDiagram
    autonumber
    participant G as inflist_grid (UI线程)
    participant C as inflist_core (UI线程)
    participant I as inflist_image
    participant A as 业务 App
    participant H as libhttp_client (worker线程)
    participant TK as 定时器 tick (UI线程)

    Note over I: URL 已由 commit_item 经 iimg_set_url 写入
    G->>C: 可见区 ±preload → request_image(id)
    C->>I: inflist_image_request(id)
    alt 有URL且未下载
        I->>I: state=LOADING·gen=当前代次
        I->>C: request_image(id, gen, url)
        C->>A: request_image(id, gen, url)
        A->>H: http_download(jpg, ...) [gen 存进 user_data]
        H-->>A: 完成 (worker线程)
        A->>C: inflist_notify_image(gen, id, path, ok)
        C->>I: inflist_image_notify → 只写静态收件箱(加锁)
        TK->>I: inflist_image_tick() 排空
        I->>I: 校验 gen → 落本地路径·state=READY
        I->>C: on_committed(id)
        C->>G: notify_item(id) → 该 cell 换上真图 ✅
    end

LRU 淘汰：图片库槽位满时淘汰最久未用的 READY 槽，并回调 remove_file 删掉盘上文件，控制磁盘占用。

4. 线程与安全模型（为什么 reset/close 不崩）

graph LR
    subgraph UI["UI / LVGL 线程（独占写库）"]
        direction TB
        OPS["get_item / commit_item<br/>set_item / set_url<br/>reset / close"]
        TICK["tick：排空收件箱 → 落库 → 刷新"]
        DB[("文字库 + 图片库<br/>(单库 · generation)")]
        OPS --> DB
        TICK --> DB
    end
    subgraph WK["http worker 线程（绝不写库）"]
        NOTIFY["inflist_notify_page / _image<br/>只写 POD"]
    end
    INBOX[["静态收件箱<br/>进程内永久存在 · 加锁<br/>(每库一个)"]]

    NOTIFY -->|加锁入队| INBOX
    INBOX -->|UI线程加锁出队| TICK

    classDef ui fill:#238636,stroke:#0b3b1b,color:#fff;
    classDef wk fill:#9e6a03,stroke:#3d2900,color:#fff;
    classDef box fill:#8957e5,stroke:#3c1e70,color:#fff;
    class OPS,TICK,DB ui;
    class NOTIFY wk;
    class INBOX box;

三道防线：

  1. 静态收件箱：跨线程通知只把 POD 拷进进程内永久存在的 static 队列，绝不触碰库内容或 LVGL 对象。即使 close 之后、http_cancel_pending() 漏网的回调迟到，也只是往常驻内存写一条信 → 安全。
  2. generation 代次：reset/close 让两库 gen++；tick 落库前校验 gen，陈旧下载结果直接丢弃（取代「双数据库来回切」）。
  3. UI 线程独写：所有库写入只在 UI 线程串行发生，worker 从不写库 → 无并发写、无需双缓冲。

对照 libhttp_client/src/guard/http_ud_guard：那用「守护+releaser」给 user_data 兜底；这里用「静态收件箱+generation」给数据库兜底，思路一致——让迟到回调永远指向有效内存。

5. reset / close 时的 generation 失效

sequenceDiagram
    autonumber
    participant A as 业务
    participant C as 协调层
    participant T as 文字库
    participant H as worker线程

    Note over T: gen = 5，page=3 下载在途(带 gen=5)
    A->>C: inflist_reset(new_total)   %% 用户切歌单
    C->>T: inflist_text_reset → gen=6, 清页槽
    H-->>C: 旧下载完成: notify_page(gen=5, page=3)
    C->>T: 入静态收件箱(安全)
    Note over T: tick 出队，校验 gen=5 ≠ 当前 6
    T->>T: 丢弃 ❌（不落库，不刷新）
    Note over T: 新代次 6 的请求各走各的，互不污染

close 同理：先 reset(gen++) 再 destroy，在途回调即便正好到达也被 gen 丢弃；句柄释放后到达的通知只进静态收件箱，下次 open 时排空。
