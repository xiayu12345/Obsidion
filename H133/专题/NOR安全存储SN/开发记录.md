## 1. 要解决什么

设备要有**掉电、再刷机还在**的硬件 SN。KTV 业务里的 `deviceSn` 是登录手机号（`ktv_phone.txt`），**不是**这个号。

全志约定 key 名 **`snum`**（还可顺带 `mac_addr` / `wifi_mac` / `bt_mac`）。

---

## 2. NOR 官方怎么存

`libkey` 三种情况：

1. private + SST 都有：写两边，读先 SST 再 private  
2. **只有 SST**：只读写 SST ← **官方所有 `sys_partition_nor.fex` 都没有 private**  
3. 只有 private：只读写 private ← NAND/eMMC 常用

ZS101 分区：`boot-resource` / `env` / `boot` / `rootfs` / `rootfs_data` / `UDISK`，没有 private。

SST 在逻辑分区前面：`(SPINOR_LOGICAL_OFFSET - SPINOR_SECURE_STORAGE_SIZE) × 512`。默认 `2016 - 64` 扇区。量产擦除（eraseflag=1）走 `sunxi_flash_spinor_special_erase`：**先擦 SST 前面（boot0/U-Boot），再从逻辑起点擦到末尾，中间 SST 不动**。

Linux：`libsst.so` → `/dev/sunxi_flash_app`（`CONFIG_SUNXI_SID`）。命令行壳是 `sst_test`（包 `libkey-demo`）。应用调库见 [libkey/操作方法.md](./libkey/操作方法.md)。

### 2.1 `CONFIG_SPINOR_SECURE_STORAGE_SIZE=64` 是干什么

**不是把 SN 改成 64 字节。** 单位是 **512 字节扇区**：`64 × 512 = 32KB`，整块 SST 仓库的大小。

SST 按 **4KB 一格** 排：一张 map + `snum` / MAC / WiFi·蓝牙 MAC / HDCP 等，大约 **8 格**。一条 SN 只占其中一格里的一小截。相对 32MB NOR 约千分之一。

`sun8iw20p1_defconfig` 的 Kconfig 默认是 **0**（不留 SST）。改成 64 是对齐官方 `sun8iw20p1_nor_defconfig`。为 0 时：没地方写号，分区擦除也不跳这块。

**不要改小或改大。** 改小少格子、擦除跳过区域和官方对不齐；改大会挤 U-Boot 和分区之间的空隙，U-Boot 镜像太大可能叠到 SST。

---

## 3. 为什么 ZS101 原来不行

官方 `sun8iw20p1_nor_defconfig` 已有：

- `CONFIG_SPINOR_SECURE_STORAGE_SIZE=64`
- `CONFIG_SUNXI_SERIAL=y`

ZS101 的 `BoardConfig.mk` 却是：

```
LICHEE_BRANDY_DEFCONF:=sun8iw20p1_defconfig
```

这份 **SST size=0、没开 SERIAL**。Linux 写进 SST 的号，开机 U-Boot 不读、cmdline 没有 `snum=`。以前用 `setenv snum` 写在 **env 分区**，全盘/分区擦除都会没。

`sst_test` 原先没编（`# CONFIG_PACKAGE_libkey-demo is not set`）。

---

## 4. 定稿改动

| 文件 | 改什么 |
|------|--------|
| `brandy/.../configs/sun8iw20p1_defconfig` | `SPINOR_SECURE_STORAGE_SIZE=64`（32KB 仓库，见 2.1）+ `SUNXI_SERIAL=y` |
| `brandy/.../board/sunxi/sunxi_bootargs.c` | `snum` 为空不拼 `androidboot.serialno`；`tmpbuf` 128→512 |
| `platform/allwinner/common/libkey/demo/main.c` | `sst_test` 读写 128/256→512 |
| `openwrt/target/h133/h133-p1_nor_ZS101/defconfig` | `CONFIG_PACKAGE_libkey-demo=y` |

开机链路：`sunxi_set_serial_num()` 从 SST 读 `snum` → `env_set` → `setargs_nor` 的 `snum=${snum}` → `update_bootargs` 再拼 `androidboot.serialno`。

长度：SST 格子约 4KB；U-Boot 读 512；cmdline `tmpbuf`/ `sst_test` 现为 512。实测约 256 字节可整段读写。

---

## 5. PhoenixSuit 擦除（实机已对）

PC 通过 `SUNXI_EFEX_ERASE_TAG` 覆盖 dts 里的 `eraseflag`（本板 dts 原值 1，允许被覆盖）。

| 界面选项 | 实测/对应 | SN | 分区 |
|----------|-----------|----|------|
| **全盘擦除升级** | `erase_flag=0x12`：Chip Erase 整片 32MB + `sunxi_secure_storage_erase_all` | **丢** | 全没 |
| **分区擦除升级** | eraseflag=1：`special_erase` 跳过 SST | **在** | env/rootfs 等擦再写 |
| **保留数据升级** | eraseflag=0：不先擦片 | **在** | 只覆盖镜像里的分区；NOR 无 private 可保 |

串口辨认全盘擦除：

```
erase_flag = 0x12
need erase flash: 18
The Chip Erase size is: 32M ...
erase secure storage: 0 ok
```

刷完 `sst_test -r snum` 若 `map is empty` / `Read snum fail`，就是被 0x12 清了，不是「没写上」。

第一次 `sst_test -w` 出现 `Item0 (Map) magic is bad` / `map is empty` / `private bare key not supported` 是 NOR 建表，正常。

## 7. 实测

写：

```
NOR secblk write OK
[private_data_write]: write data to secure storage done
[sst] snum = 1234657894…（完整串）
```

全盘擦除后再读：`map is empty`，cmdline `snum=` 空。  
分区擦除应仍能 `-r` 到同一串，cmdline 有 `snum=` 和 `androidboot.serialno=`。

写完立刻 `sst_test -r` 就能读（已 fsync），**不必 reboot**。reboot 只为让 cmdline 带上号。
