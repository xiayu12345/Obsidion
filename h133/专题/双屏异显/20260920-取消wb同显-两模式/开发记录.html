前置④ 20260918-异显仅HDMI第三模式

1. 需求

产品确定不要同显了。要的只有两种，而且都得有 HDMI 视频：

  • 「同屏」：视频同时上 LCD 和 HDMI
  • 「异屏」：视频只上 HDMI，LCD 留 UI（点歌窗是空的）

约束：应用面接口尽量不动——sunxi_disp_mode_set / get 不改名，枚举值不变， 设置页下拉还是「同屏 / 异屏」两项。

2. 决策

2.1 复用 SAME / DIFF，不另起名

④ 是三个模式（SAME 同显 / DIFF 双贴 / DIFF_HDMI 仅电视）。⑤ 只要两个。 与其新增枚举，不如把 SAME / DIFF 的含义搬过去——应用侧一行都不用改：

模式④ mask⑤ mask⑤ 行为
SAME（设置页「同屏」）13LCD+HDMI 都有视频（接手 ④ 的 DIFF）
DIFF（设置页「异屏」）32只 HDMI（接手 ④ 的 DIFF_HDMI）
DIFF_HDMI2删—

代价是语义搬家：同一个 SAME 值，④ 上是”视频贴 LCD、HDMI 看 WB 镜像”， ⑤ 上是”视频同时贴两块屏”。升级机器时 /etc/disp_mirror_mode 里的老值要能读： mode_load() 把历史的 2（老 DIFF_HDMI）迁成 DIFF，其余一律 SAME。

2.2 WB 降级成独立功能，不再参与切换

② 那一版的做法是「WB 管道常开，切模式只显隐 HDMI 上的 WB 层」， 为此加了 g_dual_display_hdmi_output 这个开关，以及 SET_HDMI_OUT / GET_HDMI_OUT 两个 ioctl。 既然不要同显了，这层耦合没有存在意义，全部拆掉。

WB 实现本身保留（disp_dual_display_enable/disable、capture、G2D 旋转、DE1 贴层）， 但产品路径上没有任何地方会拉起它：

原来会自动启 WB 的地方⑤
disp_set_hdmi_detect()：HPD 插线且 chn_cfg_mode >= 1去掉，HDMI 视频层由 tlayer 直贴
start_work()：开机 screen1 激活且 chn_cfg_mode >= 1去掉

只剩手动 DISP_DUAL_DISPLAY_ENABLE 一条路。

2.3 DISABLE ioctl 接回真实实现

② 把 DISP_DUAL_DISPLAY_DISABLE 写死成 -EINVAL（注释：拆 WB 会 scheduling while atomic， 且产品改为管道常开），disp_dual_display_disable() 挂 __maybe_unused。

⑤ 里 WB 是需要显式拉起的独立功能，ENABLE/DISABLE 成对才说得通； 而且 ioctl 是进程上下文，当初担心的 atomic 问题不成立 （真正的 bug 是 disp_unregister_sync_finish_proc() 漏 spin_unlock，② 已经修掉了）。 所以接回真实实现，去掉 __maybe_unused。

3. 改动文件

3.1 内核

文件改什么
dev_disp.c停两条 WB 自动启动路径；拆 g_dual_display_hdmi_output 整层；DISABLE 接回实现
sunxi_display2.h删 DISP_DUAL_DISPLAY_SET_HDMI_OUT / GET_HDMI_OUT 两个枚举

dev_disp.c 里拆掉的具体位置（都是 ② 的 01-kernel-dual-hdmi-out.patch 加进来的）：

  • g_dual_display_hdmi_output 变量声明
  • disp_dual_display_set_hdmi_output() / get_hdmi_output() 两个函数
  • init_hdmi_layer() 里 enable = 0 的腾层判断，和 pr_info 的条件
  • flip_hdmi_layer() 里的 return 0 提前返回，以及冗余的 enable = 1
  • work_handler() 外面那层 if (g_dual_display_hdmi_output)（展平，局部声明提回函数开头， 内核 gnu89 不允许语句后声明）
  • disp_ioctl() 里 SET/GET_HDMI_OUT 两个 case

特意保留，不要跟着删：

保留项理由
disp_dual_display_disable() 的并发修复提前清 g_dual_display_enabled、wq 先摘指针再 destroy
disp_unregister_sync_finish_proc() 的 spin_unlock 修复真 bug，与同异显无关
g_fb_clone_allow / disp_fb_clone_is_allowed/allow_set + FB_CLONE_ALLOW_SET切模式和开机时要关 fb pan clone；chn_cfg_mode < 1 的板（p1_nor_4k）靠它做 UI 克隆。注意 FB_CLONE_ALLOW_GET 无人调用，已在收尾里删（见 §7）

3.2 libuapi

文件改什么
disp_dual.h删 DIFF_HDMI 枚举；删三个 sunxi_dual_display_* 声明；ioctl 宏只留 DISP_FB_CLONE_ALLOW_SET
disp_dual.c删三个 WB 接口及其桩；video_screen_mask() 改成 SAME→3 / DIFF→2；mode_load() 迁移历史值 2；mode_apply() 退化后内联成 fb_clone_allow_off()（见 §7）
disp_mode_cli.c去掉 diff_hdmi；输出去掉 wb= / hdmi_out= 两列

3.3 应用

逻辑一行不改。 desk_setting.c、desk_setting_image.c、desk_setting_screen.c、 ktv_player_ui.c 完全不动，下拉仍是「同屏 / 异屏」。 tlayer_ctrl.c / media_session.c 只在收尾时改了两行过期注释（§7），无逻辑变更。

4. 范围是怎么锁定的

这一代动到了 ② 合进来的内核代码，容易误删，所以做了机械校验而不是凭判断：

判据：g_dual_display_hdmi_output、set/get_hdmi_output、SET/GET_HDMI_OUT 不出现在差异里 = 已精确还原成 ② 之前的样子，一行没多删。 剩下的差异应当只有「该保留的修复 + fb_clone + 本代两处」。

libuapi 那边更简单：disp_dual.c / disp_mode_cli.c / disp_dual.h 在 ② 的 02-libuapi-disp-mode.patch 里是 new file mode，整份文件都是 ② 创建的，不存在能误删的既有代码。

6. 曾经怀疑、实测已无的两项

④ 遗留的这两个问题，⑤ 上板实测都不复现。它们是被本代的解耦顺带解决的， 不是单独去修的，所以把机制记下来，免得以后又被当成待办：

6.1 异屏未插 HDMI 不回落 LCD —— 已正常

sunxi_disp_video_screen_mask() 未插时返回 1（回 LCD），判断依据是 sunxi_disp_hdmi_connected() → DISP_GET_OUTPUT_TYPE(screen1)。

内核里 bsp_disp_get_output_type() 只在 screen1 的 disp_device is_enabled() 为真时才返回 DISP_OUTPUT_TYPE_HDMI，否则给 NONE：

② 那一版之所以判不准，是因为 WB 会在 disp_set_hdmi_detect() 里被自动拉起， 连带把 screen1 撑着，is_enabled() 就跟真实插拔脱钩了。⑤ 拆掉这层耦合后， screen1 的使能重新跟着 HPD 走，这个查询自然就准了。

所以不需要再加 DISP_HDMI_HPD_GET（那条曾经试过并整体回退）。

6.2 同屏 HDMI 画面倒置 —— 不存在

一度以为 SAME 会把同一份已按 MIPI 旋转过的 buffer 同时贴两块屏。 读 dualDispPreparePerScreen() 确认不是：两块屏喂的是两份不同的参数。

索引屏喂什么
per_screen_vp[0] / rb[0]screen0 = LCDDispNvRotate90() 之后的 rotPic（即 VIDEO_WB_MIRROR_ROTATE=90 的 CPU 旋转结果）
per_screen_vp[1] / rb[1]screen1 = HDMI原始横屏 landscape_vp / landscape_rb，没有旋转

CPU 旋转只作用在 [0]，HDMI 那路结构上就拿不到旋转后的图，不会倒。

7. 收尾：清残留接口

主改动合完后又把 ② 的改动范围过了一遍，找还没人用的接口和过期的 WB 说法。 判据统一是「全树 grep 调用点为 0」，不靠感觉。

7.1 删掉的

删除项位置为什么能删
DISP_FB_CLONE_ALLOW_GETdev_disp.c 的 case + sunxi_display2.h 枚举② 加的纯排障口，全树 0 调用；它的 setter 还在用，getter 没有任何工具会调
sunxi_disp_mode_apply()disp_dual.h 声明 + disp_dual.c 实现与桩解耦 WB 后函数体退化成 (void)mode; return fb_clone_allow_off();，连 mode 都不看了；libuapi 外 0 调用。改成内部两个调用点直接调 fb_clone_allow_off()

sunxi_disp_mode_boot_sync() 也因此简化：原先 mode_load() 出来的 mode 只是喂给 mode_apply() 又被丢掉，现在直接 return fb_clone_allow_off();，行为等价。

7.2 过期注释

位置原文问题
tlayer_ctrl.cdisp_screen=1: WB mirror, rotate for MIPI only; 3: dual-diff both screens⑤ 里 disp_screen=1 是「没插 HDMI 回落 LCD」，跟 WB 镜像没关系了
media_session.c同/异显偏好开机同步（默认 SAME；DIFF 时关 WB）现在两种模式都关 fb clone，也都不碰 WB

7.3 查过但不能删的

项为什么留
VIDEO_WB_MIRROR_ROTATE名字骗人。它不是 WB 管道的东西，是视频层贴 MIPI 时的 CPU 旋转角（tlayer_ctrl.c 里 #if == 90 那段真在转 buffer），板级 -D 传入，JL_M101=90。删了 LCD 画面方向就错。它只作用于 per_screen_*[0]（LCD），HDMI 走未旋转的原图，见 §6.2
DISP_DUAL_DISPLAY_ENABLE / DISABLE / GET_EN三个都没有用户态调用方了，但这是刻意保留的 WB 独立功能的全部控制面。只删 GET_EN 会让这组口不成对，反而更难用。WB 本身要留（§2.2），控制面就跟着留
SUNXI_DISP_KTV_STATE_IDLE + /tmp/media_session_ktv.stateplayback_busy() 靠它挡播中切换；该文件由 media_session 侧真实写入，链路是通的
disp_dual.h 里 DISP_MODE_LEGACY_HDMI_ONLY从 ④ 升级的机器要靠它迁移老偏好值 2

7.4 验证

整编通过，镜像 md5 c5e57cba812e4595c714b67e4c6bbf6d。

整编时 lv_leishi_sdk_demo 报过一次 *.provides Error 1，日志里没有编译错误。 这是 OpenWrt 并行打包的老竞态（之前 kmod-fs-vfat 也中过），重跑即过，与本改动无关。
